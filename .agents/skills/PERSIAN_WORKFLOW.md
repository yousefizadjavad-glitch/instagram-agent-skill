# گردش‌کار مشترک فارسی — فاز اول MVP

این راهنما دستور مشترک چهار مهارت موجود است، نه مهارت چهاردهم یا هماهنگ‌کنندهٔ اجرایی. در کار فارسی، این راهنما و بخش «مسیر فارسی» هر مهارت بر دستورهای عمومی متعارض همان مهارت تقدم دارند. رفتار، ابزارها و مثال‌های انگلیسی به مسیر انگلیسی تعلق دارند و حفظ می‌شوند.

## بریف مشترک

پیش از تهیه متن، اطلاعات موجود را یک‌بار جمع‌بندی کنید؛ برای اطلاعات ضروریِ مفقود سؤال کنید و باقی را «نامشخص» بنویسید. پیش‌فرض تجاری یا تجربهٔ شخصی نسازید.

| ورودی | قرارداد کاری |
| --- | --- |
| موضوع | یک موضوع مشخص یا متن اولیهٔ کاربر |
| هدف | اطلاع‌رسانی، آموزش، معرفی یا هدف اعلام‌شدهٔ کاربر |
| مخاطب | گروه مخاطب و زمینهٔ لازم؛ بدون حدس ویژگی‌های شخصی |
| قالب | کپشن، ریلز یا استوری |
| لحن | `formal`، `semi-formal` یا `colloquial`؛ با انتخاب کاربر |
| خطاب | مستقل از لحن: `shoma`، `to` یا `unspecified`؛ نامشخص را خودکار به تو/شما تبدیل نکنید |
| اطلاعات تأییدشده | فقط داده‌های ارائه‌شده/تأییدشده؛ عدد، قیمت، تاریخ، مزیت، تجربه و نتیجهٔ ناموجود را نسازید |
| نام‌ها و حفاظت‌ها | صورت دقیق نام، برند، اصطلاح، URL و عبارت حساس؛ نام‌های لازم را صریحاً با `--protect` به پیشنهادگر بدهید |
| CTA | اختیاری؛ نبود آن معتبر است. در صورت درخواست، یک اقدام مرتبط، بدون وعدهٔ تازه |

## مسئولیت و گردش‌کار

۱. بریف را با کاربر روشن کنید و قالب را به مهارت موجود مربوط بسپارید.
۲. متن اولیه را کاربر یا مدل زبانی تهیه می‌کند؛ ابزارهای آفلاین فعلی تولیدکنندهٔ خلاق متن نیستند. دادهٔ مجهول را حذف یا برای روشن‌شدن متوقف کنید؛ به جای آن ادعا نسازید.
۳. اجزای قالب را جدا و نسخهٔ دقیق متن را ثابت نگه دارید. شرط، نفی، احتمال، میزان قطعیت، خطاب، نام، عدد، قیمت و لینک حفظ شوند؛ برای روانی یا جذابیت، آن‌ها را تغییر ندهید.
۴. بازبینی فارسی را طبق [مسیر فارسی ig-human](ig-human/SKILL.md) اجرا کنید. برای گفتار، متن تصویر و کارت‌ها گزارش جدا با نام جزء بدهید؛ پیوستگی کل مجموعه را نیز انسانی بررسی کنید. متن صحنه را به عنوان گفتار تحلیل نکنید.
۵. یافته‌ها، پیشنهادها، خودداری‌ها، راهنمای انسانی و محدودیت‌ها را جدا گزارش کنید. این دسته‌بندی نمایش انسانی است، نه تغییر JSON ابزارها. نبود یافته تأیید طبیعی‌بودن، صحت یا کیفیت نیست.
۶. هر پیشنهاد فقط پس از تأیید انسان قابل استفاده است؛ هیچ جایگزینی خودکار یا اعمال هم‌زمان پیشنهادهای هم‌پوشان انجام ندهید. پس از ویرایش تأییدشده، نسخهٔ تازه دوباره بازبینی شود؛ offset نسخهٔ قبل معتبر نیست.
۷. متن قابل کپی را تنها پس از تأیید انسانی نهایی مشخص کنید. انتشار، ارسال، ذخیرهٔ بریف یا نوشتن لاگ خودکار انجام نشود؛ ذخیره فقط با اجازهٔ کاربر.

این فاز فقط هماهنگی دستورهاست؛ قرارداد CLI/JSON، ابزار اجرایی، API مدل، فایل خروجی اجباری و قالب JSON تازه‌ای تعریف نمی‌کند. قواعد محدودند و حفظ معنا یا طبیعی‌بودن را تضمین نمی‌کنند.

## سه مثال فارسی مفهومی

این‌ها داده‌های فرضیِ آشکار برای توضیح قراردادند، نه نتیجهٔ اجرای ابزار یا تجربهٔ واقعی.

### کپشن

بریف: معرفی ماگ؛ مخاطب خریدار؛ `semi-formal` / `unspecified`؛ اطلاعات فرضی تأییدشده: نام «ماه  نقره‌ای»، ماگ آبی، قیمت «۴۸۰٬۰۰۰ تومان»؛ حفاظت همان نام و قیمت؛ CTA ندارد.

- شروع: «ماگ آبی ماه  نقره‌ای»
- بدنه: «قیمت: ۴۸۰٬۰۰۰ تومان»
- CTA: ندارد؛ مزیت یا تجربهٔ مصرف اضافه نشده است.

### ریلز

بریف: نمایش ساخت کاسهٔ خام؛ مخاطب علاقه‌مند به سفال؛ `colloquial` / `unspecified`؛ دادهٔ فرضی تأییدشده: گذاشتن گل، صاف‌کردن کف، بالا‌آوردن لبه؛ CTA ندارد؛ زمان واقعی نامشخص.

- هوک: «این سه مرحلهٔ ساخت کاسهٔ خامه.»
- سناریو: سه نمای جدا از مراحل ارائه‌شده، به همان ترتیب.
- گفتار: «اول گل رو می‌ذاریم، بعد کفش رو صاف می‌کنیم و لبه رو بالا میاریم.»
- متن تصویر: «گذاشتن گل» / «صاف‌کردن کف» / «بالاآوردن لبه»
- پایان: «این هم کاسهٔ خام.»؛ بدون زمان قطعی، نتیجهٔ پخت یا وعدهٔ عملکرد.

### استوری

بریف: انتخاب عنوان برای جلسهٔ مطالعه؛ مخاطب اعضای گروه؛ `semi-formal` / `shoma`؛ دو عنوان فرضی تأییدشده و محافظت‌شده «باد شمال» و «راه دور»؛ نظرسنجی به درخواست کاربر.

۱. «برای جلسهٔ مطالعه، دو عنوان داریم.»
۲. «باد شمال / راه دور»
۳. «شما کدام عنوان را ترجیح می‌دهید؟»؛ نظرسنجی با همان دو گزینه.

این انتخاب دربارهٔ عنوان است؛ نویسنده، محتوای کتاب یا وعدهٔ برگزاری ساخته نمی‌شود. حذف تعامل نیز خروجی معتبر است.
