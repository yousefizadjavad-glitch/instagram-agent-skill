# گردش‌کار مشترک فارسی — فاز اول MVP

این راهنما دستور مشترک چهار مهارت موجود است، نه مهارت چهاردهم یا هماهنگ‌کنندهٔ اجرایی. در کار فارسی، این راهنما و بخش «مسیر فارسی» هر مهارت بر دستورهای عمومی متعارض همان مهارت تقدم دارند. رفتار، ابزارها و مثال‌های انگلیسی به مسیر انگلیسی تعلق دارند و حفظ می‌شوند.

## بریف مشترک

پیش از تهیه متن، اطلاعات موجود را یک‌بار جمع‌بندی کنید؛ برای اطلاعات ضروریِ مفقود سؤال کنید و باقی را «نامشخص» بنویسید. پیش‌فرض تجاری یا تجربهٔ شخصی نسازید.

| ورودی | قرارداد کاری |
| --- | --- |
| موضوع | یک موضوع مشخص یا متن اولیهٔ کاربر |
| هدف | اطلاع‌رسانی، آموزش، معرفی یا هدف اعلام‌شدهٔ کاربر |
| مخاطب | گروه مخاطب و زمینهٔ لازم؛ بدون حدس ویژگی‌های شخصی |
| قالب | کپشن، ریلز یا استوری |
| لحن | `formal`، `semi-formal` یا `colloquial`؛ با انتخاب کاربر |
| خطاب | مستقل از لحن: `shoma`، `to` یا `unspecified`؛ نامشخص را خودکار به تو/شما تبدیل نکنید |
| اطلاعات تأییدشده | فقط داده‌های ارائه‌شده/تأییدشده؛ عدد، قیمت، تاریخ، مزیت، تجربه و نتیجهٔ ناموجود را نسازید |
| نام‌ها و حفاظت‌ها | صورت دقیق نام، برند، اصطلاح، URL و عبارت حساس؛ نام‌های لازم را صریحاً با `--protect` به پیشنهادگر بدهید |
| CTA | اختیاری؛ نبود آن معتبر است. در صورت درخواست، یک اقدام مرتبط، بدون وعدهٔ تازه |

## مسئولیت و گردش‌کار

۱. بریف را با کاربر روشن کنید و قالب را به مهارت موجود مربوط بسپارید.
۲. متن اولیه را کاربر یا مدل زبانی تهیه می‌کند؛ ابزارهای آفلاین فعلی تولیدکنندهٔ خلاق متن نیستند. دادهٔ مجهول را حذف یا برای روشن‌شدن متوقف کنید؛ به جای آن ادعا نسازید.
۳. اجزای قالب را جدا و نسخهٔ دقیق متن را ثابت نگه دارید. شرط، نفی، احتمال، میزان قطعیت، خطاب، نام، عدد، قیمت و لینک حفظ شوند؛ برای روانی یا جذابیت، آن‌ها را تغییر ندهید.
۴. بازبینی فارسی را طبق [مسیر فارسی ig-human](ig-human/SKILL.md) اجرا کنید. برای گفتار، متن تصویر و کارت‌ها گزارش جدا با نام جزء بدهید؛ پیوستگی کل مجموعه را نیز انسانی بررسی کنید. متن صحنه را به عنوان گفتار تحلیل نکنید.
۵. یافته‌ها، پیشنهادها، خودداری‌ها، راهنمای انسانی و محدودیت‌ها را جدا گزارش کنید. این دسته‌بندی نمایش انسانی است، نه تغییر JSON ابزارها. نبود یافته تأیید طبیعی‌بودن، صحت یا کیفیت نیست.
۶. هر پیشنهاد فقط پس از تأیید انسان قابل استفاده است؛ هیچ جایگزینی خودکار یا اعمال هم‌زمان پیشنهادهای هم‌پوشان انجام ندهید. پس از ویرایش تأییدشده، نسخهٔ تازه دوباره بازبینی شود؛ offset نسخهٔ قبل معتبر نیست.
۷. متن قابل کپی را تنها پس از تأیید انسانی نهایی مشخص کنید. انتشار، ارسال، ذخیرهٔ بریف یا نوشتن لاگ خودکار انجام نشود؛ ذخیره فقط با اجازهٔ کاربر.

این فاز فقط هماهنگی دستورهاست؛ قرارداد CLI/JSON، ابزار اجرایی، API مدل، فایل خروجی اجباری و قالب JSON تازه‌ای تعریف نمی‌کند. قواعد محدودند و حفظ معنا یا طبیعی‌بودن را تضمین نمی‌کنند.

## سه مثال فارسی مفهومی

این‌ها داده‌های فرضیِ آشکار برای توضیح قراردادند، نه نتیجهٔ اجرای ابزار یا تجربهٔ واقعی.

### کپشن

بریف: معرفی ماگ؛ مخاطب خریدار؛ `semi-formal` / `unspecified`؛ اطلاعات فرضی تأییدشده: نام «ماه  نقره‌ای»، ماگ آبی، قیمت «۴۸۰٬۰۰۰ تومان»؛ حفاظت همان نام و قیمت؛ CTA ندارد.

- شروع: «ماگ آبی ماه  نقره‌ای»
- بدنه: «قیمت: ۴۸۰٬۰۰۰ تومان»
- CTA: ندارد؛ مزیت یا تجربهٔ مصرف اضافه نشده است.

### ریلز

بریف: نمایش ساخت کاسهٔ خام؛ مخاطب علاقه‌مند به سفال؛ `colloquial` / `unspecified`؛ دادهٔ فرضی تأییدشده: گذاشتن گل، صاف‌کردن کف، بالا‌آوردن لبه؛ CTA ندارد؛ زمان واقعی نامشخص.

- هوک: «این سه مرحلهٔ ساخت کاسهٔ خامه.»
- سناریو: سه نمای جدا از مراحل ارائه‌شده، به همان ترتیب.
- گفتار: «اول گل رو می‌ذاریم، بعد کفش رو صاف می‌کنیم و لبه رو بالا میاریم.»
- متن تصویر: «گذاشتن گل» / «صاف‌کردن کف» / «بالاآوردن لبه»
- پایان: «این هم کاسهٔ خام.»؛ بدون زمان قطعی، نتیجهٔ پخت یا وعدهٔ عملکرد.

### استوری

بریف: انتخاب عنوان برای جلسهٔ مطالعه؛ مخاطب اعضای گروه؛ `semi-formal` / `shoma`؛ دو عنوان فرضی تأییدشده و محافظت‌شده «باد شمال» و «راه دور»؛ نظرسنجی به درخواست کاربر.

۱. «برای جلسهٔ مطالعه، دو عنوان داریم.»
۲. «باد شمال / راه دور»
۳. «شما کدام عنوان را ترجیح می‌دهید؟»؛ نظرسنجی با همان دو گزینه.

این انتخاب دربارهٔ عنوان است؛ نویسنده، محتوای کتاب یا وعدهٔ برگزاری ساخته نمی‌شود. حذف تعامل نیز خروجی معتبر است.

## فاز دوم MVP: هماهنگ‌کنندهٔ آفلاین مستقل

[هماهنگ‌کننده](persian_workflow.py) مهارت تازه‌ای نیست؛ چهار تابع موجود را بدون تغییر قراردادشان فراخوانی می‌کند. هیچ مدل یا شبکه‌ای فراخوانی نمی‌شود. بخش «این فاز فقط هماهنگی دستورهاست» در بالا شرح فاز اول است؛ این بخش اجرای مستقل فاز دوم را تعریف می‌کند.

### ورودی و CLI

از ریشهٔ مخزن، فایل JSON UTF-8 موجود را بخوانید یا JSON را با stdin بدهید؛ خروجی همیشه JSON روی stdout است. ابزار فایل خروجی، حافظهٔ دائمی، انتشار یا گزینهٔ apply ندارد. خطای ورودی کد خروج ۲ و stderr می‌دهد؛ موفقیت کد صفر به معنی تأیید کیفیت نیست.

```bash
python3 .agents/skills/persian_workflow.py brief.json
cat brief.json | python3 .agents/skills/persian_workflow.py -
python3 .agents/skills/persian_workflow.py brief.json --decisions decisions.json
```

نمونهٔ ورودی مصنوعی کپشن:

```json
{
  "format": "caption",
  "topic": "سفال",
  "goal": "معرفی",
  "audience": "علاقه‌مندان",
  "target_tone": "semi-formal",
  "target_address": "unspecified",
  "verified_facts": ["قیمت: ۴۸۰٬۰۰۰ تومان"],
  "protected_terms": ["ماه  نقره‌ای"],
  "optional_cta": null,
  "draft": {"text": "ماه  نقره‌ای؛ امروز  سفال داریم. قیمت: ۴۸۰٬۰۰۰ تومان"}
}
```

تمام فیلدهای بریف جدول بالا لازم‌اند؛ `optional_cta` و `draft` می‌توانند حذف یا null باشند. واقعیت‌ها و حفاظت‌ها آرایهٔ رشته‌های غیرخالی‌اند؛ خالی‌بودن خود آرایه مجاز است. فیلد ناشناخته و کلید JSON تکراری رد می‌شوند. لحن و خطاب از همان enumهای بریف استفاده می‌کنند. CTA ورودی فقط زمینه است؛ به متن افزوده نمی‌شود.

شکل `draft` برای سه قالب:

- کپشن: `{"text":"متن"}`.
- ریلز: `{"hook":"هوک","spoken_script":"گفتار","on_screen_text":"متن تصویر","ending":"پایان"}`؛ هر چهار رشته لازم‌اند. چند خط متن تصویر در همان رشته مجاز است. سناریوی تصویربرداری ساختاریافته هنوز ورودی اجرایی نیست.
- استوری: `{"cards":[{"number":1,"text":"کارت اول"},{"number":2,"text":"کارت دوم"}]}`؛ شماره‌ها صحیح، متوالی و از ۱ باشند. متن هر بخش غیرخالی است.

بدون draft، `mode=brief_only` و `generation_instruction` شامل بریف و محدودیت‌ها برمی‌گردد؛ `generated_draft=false` و هیچ متن خلاقی تولید نمی‌شود. اطلاعات تأییدشده حقیقت‌سنجی نمی‌شوند؛ این نام یعنی کاربر آن‌ها را تأیید کرده است.

### خروجی و نسخه‌بندی

قرارداد هماهنگ‌کننده مستقل و `schema_version=1` است. `source_hash` در ریشه SHA256 نمایش canonical JSON کل درخواست (مرتب‌سازی کلیدها، بدون فاصلهٔ قالب‌بندی) است؛ ترتیب آرایه‌ها مهم است. هر بخش `section_id` پایدار، `source_text` عین ورودی و `source_hash` برابر SHA256 متن UTF-8 دارد:

- `caption.text`
- `reel.hook`، `reel.spoken_script`، `reel.on_screen_text`، `reel.ending`
- `story.card.1` و به همین ترتیب

هر بخش و گزارش ریشه `findings`، `suggestions`، `guidance`، `abstentions` و `limitations` را جدا نگه می‌دارند. یافته‌ها/پیشنهادها/راهنماها/خودداری‌ها با شناسه و هش بخش منتسب‌اند؛ محدودیت‌ها رشته‌های توضیحی‌اند. گزارش ریشه مجموعهٔ موارد بخش‌هاست؛ یک مورد را دوبار نشمارید. `raw_reports` هر بخش، خروجی دست‌نخوردهٔ چهار تابع فعلی است؛ نسخهٔ ۱ پیشنهادگر تغییر نکرده است. شناسهٔ پیشنهاد در لایهٔ هماهنگ‌کننده با بخش و نام ابزار پیشوند می‌گیرد؛ تعارض مکانیکی/زبانی نیز محاسبه می‌شود.

برای استوری، `sequence_review` کارت‌ها را با یک newline به هم متصل و فقط تغییر احتمالی خطاب را تکمیلی بررسی می‌کند؛ `section_map` و `evidence.section_spans` نگاشت offset به کارت اصلی را می‌دهند. offsetها اندیس code point پایتون، از صفر و end انحصاری‌اند؛ اندیس بایت یا UTF-16 نیستند. این مسیر تشخیص جامع گوینده یا پیوستگی معنایی نیست؛ جمله یا نقل‌قول را میان کارت‌ها ناقص نکنید. هش کل توالی نیز مستقل است.

### تصمیم صریح بدون اعمال تغییر

فایل `decisions.json` آرایه است. هر تصمیم را از همان گزارش جاری بردارید، مثلاً شکل زیر (مقادیر نمونهٔ جای‌نگهدار باید با خروجی واقعی جایگزین شوند):

```json
[{
  "section_id": "caption.text",
  "suggestion_id": "caption.text:persian_rewrite:s1",
  "source_hash": "SHA256 دقیق بخش از گزارش",
  "request_hash": "source_hash ریشه گزارش",
  "start": 0,
  "end": 2,
  "before": "  ",
  "action": "accept"
}]
```

`action` فقط `accept` یا `reject` است؛ هیچ تصمیم پیش‌فرضی وجود ندارد. ابزار پیشنهادها را از درخواست جاری مجدداً استخراج می‌کند؛ هش بریف و متن، شناسه، offset و before باید تطبیق کنند. تغییر متن، مخاطب، لحن، حفاظت یا هر جزء درخواست، تصمیم پیشین را نامعتبر می‌کند. انتخاب تکراری، ناشناخته و پذیرش پیشنهادهای هم‌پوشان رد می‌شود؛ هیچ تصمیمی در اجرای بعد به یاد نمی‌ماند.

حتی پس از پذیرش، `applied=false` است: فقط رسید تصمیم و replacement بررسی‌شده برمی‌گردد، نه متن ویرایش‌شده. انسان بیرون از ابزار ویرایش را انجام می‌دهد و متن تازه باید دوباره بازبینی شود. پذیرش پیشنهاد تأیید نهایی کل محتوا یا اجازهٔ انتشار نیست.

نام‌ها و verified_facts به صورت عین رشته به حفاظت هر دو پیشنهادگر داده می‌شوند؛ URL، عدد، قیمت و تاریخ نیز تحت قواعد حفاظت موجودند. بازنویسی یا تأیید معنایی واقعیت‌ها انجام نمی‌شود؛ ادعاهای تازه‌ای که از قبل در draft باشند ممکن است کشف نشوند. شروط، نفی، کنایه، بافت کارت‌ها و نام‌های معرفی‌نشده همچنان نیازمند انسان‌اند. هیچ امتیاز طبیعی‌بودن یا تضمین معنا ارائه نمی‌شود.

## اعتبارسنج محدود اطلاعات ثابت

[اعتبارسنج مستقل](persian_fact_checks.py) از طریق هماهنگ‌کننده اجرا می‌شود و هیچ‌یک از چهار ابزار فارسی را تغییر نمی‌دهد. قرارداد ورودی `verified_facts`، `protected_terms` و `draft` همان است. خروجی افزودهٔ ریشه با نام `fact_checks` شامل `fact_checks`، `mismatches`، `ambiguous`، `limitations`، `source_hash` و `section_id` است؛ این بخش مستقل از یافته‌های سبک و پیشنهادهای اصلاح است و پیشنهاد جایگزینی ندارد. شناسهٔ ریشهٔ آن `workflow` و هش آن همان هش درخواست است؛ هر مقایسه شناسه و هش بخش اصلی و شواهد بریف/متن با offset مستقل دارد.

دامنهٔ محدود مقایسه:

- قیمت عددی با واحد صریح تومان یا ریال؛ ارقام فارسی، عربی و لاتین و جداکننده‌های هزارگان `,` و `٬` نرمال می‌شوند. اعشار `.` و `٫` پشتیبانی می‌شوند؛ تومان به ریال تبدیل نمی‌شود. «۴۸۰٬۰۰۰ تومان» و «480,000 تومان» تطابق لفظی محدود دارند؛ «۹۸۰ گرم» قیمت نیست.
- تاریخ عددی `سال/ماه/روز` یا `سال-ماه-روز` با سال چهاررقمی؛ صفر ابتدایی نادیده گرفته می‌شود. تشخیص تقویم و اعتبار تقویمی انجام نمی‌شود؛ نقش‌های تحویل/تولید/انقضا/سفارش/پرداخت محافظه‌کارانه به بررسی انسانی می‌روند.
- کد فقط با `کد محصول:`، `شناسه محصول:` یا `شناسهٔ محصول:`؛ ارقام نرمال می‌شوند، حروف و خط تیره/زیرخط حفظ می‌شوند. کد بی‌نشانگر حدس زده نمی‌شود.
- نام فقط با `برند:` یا `نام محصول:` در واقعیت تأییدشده و با عین نام در `protected_terms` مبنا می‌شود. برای نمونه `verified_facts=["برند: ماه  نقره‌ای"]` و `protected_terms=["ماه  نقره‌ای"]`. فاصلهٔ داخل نام بخشی از هویت لفظی آن است. یک عبارت محافظت‌شدهٔ بی‌نشانگر به‌تنهایی نام برند محسوب نمی‌شود.

مقایسهٔ قطعی محدود به یک مقدار مبنا و یک مقدار مشاهده‌شده از همان دسته، با انتساب تک‌محصولی ضمنی است. چند مقدار/محصول صریح، واحد متفاوت، شرط/نفی/نقل‌قول یا زمینهٔ حساس شناسایی‌شده `ambiguous` و `needs_review` می‌گیرند. این تشخیص بافت جامع نیست. نبود مقدار در متن یا نبود مبنای قابل مقایسه تناقض نیست و `not_checked` ممکن است برگردد. URL منبع استخراج عدد نیست.

`mismatch` فقط تعارض عبارات صریح است و نیازمند انسان؛ `matched_explicit_value` فقط برابری مقدارِ محدود است، نه تأیید کلی صحت. `limited_comparison` نیز هیچ مجوز انتشار یا پذیرش خودکار نمی‌دهد. واقعیت تازه ساخته و هیچ عدد، نام یا متن اصلاح نمی‌شود. این مسیر نمی‌تواند تمام محصولات بدون نشانگر یا نقش‌های ضمنی قیمت/تاریخ را بفهمد؛ گزارش مبهم را به تطابق تبدیل نکنید.

نوع تمام فیلدهای رشته‌ای تصمیم پیش از lookup بررسی می‌شود. مثلاً `section_id=[]` با کد خروج ۲ و پیام `decision.section_id must be a string` رد می‌شود؛ رفتار `accept/reject`، کنترل هش، offset و before و `applied=false` حفظ شده است.

برای قیمت، پیشوند عمومی «قیمت:» یا مقدار مستقل مبنای انتساب محدود است؛ هزینهٔ ارسال، قیمتِ محصول نامشخص و نقش‌های نامعلوم به بررسی انسانی می‌روند، نه هشدار تناقض قطعی.
